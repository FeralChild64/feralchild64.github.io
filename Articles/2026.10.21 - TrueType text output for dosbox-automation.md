# TrueType text output for _dosbox-automation_

> **Note:** This post describes an upcoming [_dosbox-automation_](https://github.com/dosbox-automation/dosbox-automation) functionality (contributed by me, with some fixes and ideas from [@shakeyourbunny](https://github.com/shakeyourbunny)), which is already merged to the main GIT branch, but is not yet available to end users. It is intended to be a part of the next major release.
> 
> I've written the feature without any AI assistance - everything was handcrafted :)

So, what's this all about? When in text mode, _DOSBox_ takes the font (like 8x16 resolution - very low by today's standards) from the emulated machine and uses it to construct a bitmap image. Depending on the fork and configuration, post-processing might be applied to make the image look more like a real CRT image:

<img width="2880" height="2160" alt="nc-VGA" src="https://github.com/user-attachments/assets/67c9f551-3adc-4f7f-aa5a-1778d02642b3" /><br />

Such post-processing (this particular shader was written by [John Novak](https://github.com/johnnovak) for the [DOSBox Staging](https://github.com/dosbox-staging/dosbox-staging) project, based on some earlier works) is nice for gaming, but prolonged work with such a text console might be tiring.

We can disable the post-processing and enable bilinear filtering instead:

<img width="2880" height="2160" alt="nc-VGA-bilinear" src="https://github.com/user-attachments/assets/6e29f766-22ca-4e6a-8069-a25199d81331" /><br />

But now the screen looks blurry and jagged (click on the image to zoom it out).

And here comes the TrueType font output - if we set `ttf_output = true` in the config file, the results are going to look like this:

<img width="2880" height="2160" alt="nc-TTF" src="https://github.com/user-attachments/assets/297bc3a6-b789-4a5b-90e4-34a3afafeb14" /><br />

The font used here is the _Flexi IBM VGA_ font (https://int10h.org/blog/2018/05/flexi-ibm-vga-scalable-truetype-font/) by [@VileR](https://github.com/viler-int10h), which is going to be bundled with _dosbox-automation_. It keeps the style of the old VGA text mode and provides quite a lot of glyphs - we can display around 75 DOS code pages, including probably all the most popular ones.

If you prefer a more modern look, possibly the same as your OS terminal, you can change the font. For example, `ttf_font = LiberationMono-Regular` (providing that you have this font installed) produces the following image:

One might think the implementation of such a feature should be easy and straightforward - well, it is not :)

One challenge is converting the DOS characters (values from 0 to 255, values have different meaning depending on the code page) to the modern Unicode character set (the Unicode standard currently defines over 300,000 characters) - in reality, a specialized Unicode engine is needed for this, as off-the-shelf ones have a very limited support for DOS code pages. Thankfully, the one _dosbox-automation_ uses (written by me a few years ago, supporting over 170 unique DOS code pages, plus some duplicates) only needed some really minor tweaks to be usable.

Certain exotic code pages need a character composition engine able to render characters by combining a base glyph with separate combining marks code points; the current implementation can't do this (sorry, Lithuanians...) - this might get implemented one day, we'll see.

Another challenge is the performance - a 80x25 screen mode means up to 2000 vector characters needs to be rendered 70 times per second. This is a lot, especially for modern high resolution (like 4K or even more) displays.

Various optimization techniques are used to speed it up - once the window resolution is established, all the 256 current code page characters are pre-rendered in greyscale to save time later. Applying the foreground/background colors happens in a way which makes it easy for the compiler to use the specialized SIMD (like _Intel SSE_ or _ARM Neon_) CPU instructions. Plus, line caching is involved (if the color palette is unchanged, we just need to compare two bytes to check if the particular screen character is up to date) to limit the unnecessary character redraw.

This way, the performance is acceptable for normal work (some special cases, like the [BB demo](https://aa-project.sourceforge.net/bb/), make the line caching useless), though still inferior to the classic rendering.

And that's still not everything - you can't just let a TrueType engine (the implementation uses the _FreeType_ library) render the character and assume everything is going to be correct. With the bundled font, this is mostly the case, but for other popular fonts... let's see one example:

<img width="585" height="389" alt="nc-TTF-alt-nocorrections-zoom" src="https://github.com/user-attachments/assets/81ccf55b-67aa-49fd-8988-c9cdd4215d01" /><br />

The _dosbox-automation_ implementation (just like every modern terminal application) has some measures to prevent such gaps (resulting from anti-aliasing or font design) and certain other visual artifacts from appearing.

It should be able to do the job most of the time, but still has some limitations. For some fonts, the shade characters (U+2591, U+2592, U+2593 - ░, ▒, ▓, respectively) won't look right when placed one next to another, and probably not much can be done about it.

In a few cases (ligatures, hryvnia currency sign, etc.), the TrueType output can render the characters even if they are missing in the selected font, by combining characters which are available. Results might vary depending on the font and the character, but at least the code page can be supported. For some code pages this is the only realistic way to handle them, as they use characters not present in the Unicode standard - I had to assign private Unicode IDs to such DOS characters. 

See the character 0x9B below (a _zł_ ligature) - this is the PLN currency symbol, as found on some old typewriters, not covered by the Unicode standard, drawn by cramping two characters together:

<img width="2880" height="2160" alt="cp-991" src="https://github.com/user-attachments/assets/d9aa1d57-d6c8-44a5-8375-66ca4cbc377c" /><br />

Another issue which has to be handled - some text mode DOS applications redefine the screen font, so that their user interface is richer.

If we blindly replace such redefined font, we are going to get a screen containing garbage characters:

<img width="2880" height="2160" alt="tetepack-garbage" src="https://github.com/user-attachments/assets/8d70571d-8fd3-45ea-b9f6-50ba8bb370f0" /><br />

while the proper appearance of the application is:

<img width="2939" height="2160" alt="tetepack-correct" src="https://github.com/user-attachments/assets/1c9be9fc-b8d2-4d1c-be37-789137967747" /><br />

To prevent such issues, the TrueType output code observes writes to memory areas which define the screen font. If it detects that the screen font is altered, it reverts to the normal, old-style rendering method, for as long as the screen font remains modified - afterwards it returns to the TrueType output. Same happens when a custom CPI file (DOS format screen font) is loaded.

Last, but not least - we have a few aspect ratio settings to choose from (see the `ttf_aspect` option). You can force the 4:3 screen proportions, use the selected TrueType font aspect ratio, or expand the image in a widescreen-friendly way, trying to preserve the character aspect ratio from the standard 80x25 screen mode, like below (_DOS Navigator OSP 6.4.0_ using a 94x25 resolution):

<img width="3102" height="2025" alt="dn-widescreen" src="https://github.com/user-attachments/assets/7a5bcdba-16ef-4664-ac8f-479dbee2636d" /><br />

And here is the [BB demo](https://aa-project.sourceforge.net/bb/) in high resolution:

<img width="3828" height="1980" alt="bb-widescreen" src="https://github.com/user-attachments/assets/c8537362-e1da-4328-a41e-471946dc7d1a" /><br />

The `aspect = stretch` setting is also honored - you can make the text mode fill the entire window/screen.
